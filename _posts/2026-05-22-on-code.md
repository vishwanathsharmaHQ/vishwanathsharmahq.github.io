title: on code
lede: Twenty years of writing it, and still learning to.
date: 2026-05-22
---

Code is prose that runs. The best programmers I know are, without exception, careful readers. They notice a poorly named variable the way an editor notices a comma splice. It's not fussiness; it's care. Names are the interface between your intention and the next person's understanding, and both of those people might be you.

The temptation, when you're new, is to write clever code. Clever code is a form of showing off. It has a place — sometimes cleverness is what the problem requires — but most of the time it produces bugs that its own author can't debug six months later. The mature move is to write code so obvious it looks like anyone could have written it.

I've come to believe that most of the value in a codebase is not in the code itself but in the shared understanding of it. When a team knows why a decision was made, refactors are cheap. When they don't, every change is dangerous. That's why the commit messages matter, and the README matters, and the offhand comment left by someone who has since moved on matters. Code is a fossil record. Read carefully.

Testing has been the biggest shift in my thinking over the last five years. I used to write tests because I was supposed to. Now I write them because they let me sleep. A test is a promise from past me to future me: I understood what this code did, and here is the evidence. When the test breaks, it's the version of me who wrote it, tapping me on the shoulder from three years ago.

Abstractions are a debt you take out against the future. Sometimes the loan is worth it; sometimes you're paying interest on a purchase you never actually made. Ask yourself: how many places does this abstraction actually get reused? If the answer is one, you don't have an abstraction. You have a wrapper. Delete the wrapper.

The biggest lesson has been about deleting code. Every line of code is a small liability. The best change I make in a given week is often a change that removes more than it adds. This is unintuitive to junior engineers, who — reasonably — think their job is to write code. The senior version of the job is to write as little as possible while still delivering the outcome.

None of this is unique to code. It's just craft, applied to a particular medium. The programmers I admire most are the ones who would have been great at whatever they did. They pay attention. They rewrite. They don't confuse motion with progress. They know the difference between a problem that is hard and a problem that is annoying, and they don't mistake either one for the other.
